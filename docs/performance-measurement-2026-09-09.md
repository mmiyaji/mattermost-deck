# 描画パフォーマンスの改善と計測（2026-09-09）

通信ログを表示するコンポーネントだけを更新する変更と、変更のないポーリング結果の状態を再利用する変更を取り込んだ。投稿一覧の ResizeObserver もマウント中は再利用する。

## 実測結果

2026-09-09 00:43 JST、Windows / Intel Core i5-13400F / Chromium 147.0.7727.15 / Node v22.22.0。時間は60回更新の合計の中央値。

| 対象 | 変更前 | 最終版 |
| --- | ---: | ---: |
| ログ更新の同期処理時間 | 986.2 ms | 0.1 ms |
| ログ更新による親のコミット数 | 60 | 0 |
| 同内容の投稿配列更新の同期処理時間 | 960.8 ms | 5.0 ms |
| 同内容の投稿配列更新による親のコミット数 | 60 | 0 |
| 投稿配列更新で作成されたResizeObserver | 180 | 0 |

投稿比較だけを無効にした `polling-control` と最終版で、内容が変わる更新も比較した。100件目を毎回編集する60回更新では **979.9 ms → 1,011.2 ms（約3.2%増）**。この条件では比較処理を追加しても描画を省けず、速度向上はない。無変更の更新で大幅に処理を省けることとのトレードオフとして採用した。大きな添付メタデータを持つ投稿や実環境の変更頻度については未計測。

ログ分離とResizeObserver再利用だけの中間版では、同内容の投稿配列更新は988.5 msだった。Observer作成数の削減だけでは時間短縮は確認できなかった。

## 計測範囲

- production React と Playwright Chromium で、実際の `PostList`、ログ購読フック、投稿比較関数を実行。
- 3ペイン × 100投稿、コンパクト表示、固定の本文と日時。共通の fixture 親が100投稿の配列を3つの一覧へ渡す。
- ログ更新60回、同内容の投稿配列更新60回、末尾の投稿を編集する更新60回を、それぞれ `flushSync` で確定させる。
- ウォームアップ後に各条件5回。条件の実行順を交互に反転し、同期処理時間の中央値と親のコミット回数、Observerの作成数を比較。
- ログ20件の保持、診断表示を後から開いた場合の取得、WebSocketログの反映、編集した本文のDOM反映、ペインのサイズ変更もブラウザ内で検証。
- 比較用のバンドルを編集前後で保存し、同じバンドルを繰り返し実行。詳細な各回の値・環境・バンドルのSHA-256は `test-results/render-performance/comparison.json` に保存する。

これは実ブラウザでの部品ベンチマークであり、App全体やMattermostとの通信を含む計測ではない。実アプリでは各ペインが個別の状態を持ち、更新表示・ユーザーディレクトリ等の変更による描画も残る。`flushSync` によって更新を個別に確定させているため、通常のバッチ処理とも条件が異なる。数値をそのままアプリ全体の高速化率とは扱わない。

## 採用した変更

1. **ログの更新範囲を診断ペインに限定**
   - Appごとに直近20件を保持するストアを作成し、DiagnosticsColumnが `useSyncExternalStore` で購読する。
   - 診断ペインを閉じていてもログは保持し、Appのアンマウントでイベントリスナーを解除する。
   - ログ更新によるfixture親のコミットが60回から0回になった。
2. **同一内容のポーリング結果を再利用**
   - チャンネル・DM・検索・保存済みペインで、投稿と表示状態が同じなら既存の状態を返す。
   - 投稿IDや更新日時だけでは判定せず、JSON APIの投稿全体を比較する。本文・添付・props・リアクション等の変更も反映する。
   - 投稿数は既存の100件上限で制限される。JSONのキー順序が変わった場合は再利用を見送り、更新を優先する。
   - エラー、ページ番号、追加読み込み状態等が変わった場合は状態を更新する。削除の反映と通信中に届いたリアルタイム投稿の保持は既存の統合処理に従う。
3. **ResizeObserverの再利用**
   - PostListの監視対象はマウント中に変わらないため、投稿配列の変更を監視登録の依存関係から外した。
   - 60回の投稿配列更新に伴うObserverの作成が180回から0回になった。単独の実行時間短縮は確認できておらず、採用理由は不要な生成・解除・初期計測の削減。

一覧の仮想化やIntersectionObserverの共有は今回変更していない。スクロール位置、可変の行高、フォーカスへの影響を含めて別に評価する。

## 再実行

変更前にバンドルを保存し、変更後のバンドルと比較する。

```powershell
node scripts/measure-render-performance.mjs capture baseline
# コードを変更した後
node scripts/measure-render-performance.mjs capture final
node scripts/measure-render-performance.mjs compare baseline final
```

投稿比較の追加コストを切り分ける場合は、同じソースでfixtureの投稿再利用だけを無効化した対照を作る。

```powershell
node scripts/measure-render-performance.mjs capture polling-control --no-post-reuse
node scripts/measure-render-performance.mjs compare polling-control final
```

`baseline` は今回の作業開始時点の未コミット変更を含むコード。`candidate` はログ分離とResizeObserver再利用だけを適用した中間版。既存のbaselineを保持する場合は同じラベルで再captureしない。バンドルと各回のJSONはgit管理外なので、必要に応じて別途保管する。
