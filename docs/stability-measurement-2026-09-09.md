# 長時間起動に向けた改善と検証（2026-09-09）

前回の描画改善に加えて、WebSocketの復帰経路、画面の監視リソース、診断ログ保存失敗への対応を改善した。

## 修正した内容

### WebSocketの停止状態からの復帰

接続開始後、ソケットが開かない場合や認証応答が来ない場合に、再接続へ進まないことを修正前のテストで再現した。

- 接続開始から認証完了までの待機を30秒で打ち切り、既存のバックオフに従って再接続する。
- heartbeatの応答待ち、送信例外、transportのerrorでも、closeイベントの到着を待たずにソケットを切り離す。
- ソケットごとのイベント購読をAbortControllerで解除する。古い接続から遅れて届くイベントが、新しい接続に作用しない。
- 認証完了・認証拒否・切断・offline・破棄時に対応するタイマーを解除する。
- `null`、配列、プリミティブ値など、JSONとしては正しいがイベントの形式でないメッセージを無視する。

認証に実際に30秒以上かかる環境では再試行が発生する。タイマーの動作はブラウザのバックグラウンド制限を受けるため、壁時計で必ず30秒以内に復帰するという保証ではない。

### IntersectionObserverの共有と解除

同じroot・rootMargin・thresholdの監視を共有する。最後の購読を解除すると、対象要素の登録を外し、Observerを切断してpoolから削除する。rootの管理にはWeakMapを使う。

複数要素をまとめて通知された場合もすべて処理する。同じ要素を複数のコンポーネントが購読した場合は個別に解除でき、後から購読する側には直近の可視状態を伝える。

### 診断ログの保存失敗

Chromeストレージの容量不足や拡張機能コンテキストの無効化による保存拒否を処理する。定期保存・設定切替・ログ消去から未処理のPromise拒否を発生させない。メモリ上の直近500件の上限は維持し、次のログ追加時に保存が成功すれば再び永続化できる。

## 検証結果

### 実ブラウザでの開閉反復

production React / Chromium 147.0.7727.15。実際のPostListと可視状態フックで、3ペイン×100投稿を初回表示後200回再マウントした。各解除後の監視対象数を確認し、10回ごとに待機フレームとGCを挟んでDOM・イベントリスナー・ヒープを記録した。

| 指標 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 初回表示のIntersectionObserver作成数 | 300 | 3 |
| 初回＋200回再マウントでの累計作成数 | 60,300 | 603 |
| 毎回の解除後の監視対象数 | 0 | 0 |
| 初回解除後 → 最終解除後のDOM数 | 14 → 14 | 14 → 14 |
| 初回解除後 → 最終解除後のJSイベントリスナー数 | 155 → 155 | 155 → 155 |
| GC後のJSヒープ（byte） | 3,080,384 → 3,602,264 | 3,088,000 → 3,611,224 |

今回確認できた改善はObserverの生成数削減。修正前も解除後に監視対象は残っておらず、既存のDOMリークを修復したという結果ではない。ヒープは両条件で同程度増えており、この計測からヒープ使用量の削減や長期のリーク不在を断定しない。

計測ファイルは `test-results/render-performance/stability.json`。前後の固定バンドルは同じディレクトリの `stability-before.js` と `stability-after.js`。いずれもgit管理外。

```powershell
# 変更前に保存
node scripts/measure-render-performance.mjs capture stability-before
# 変更後に保存
node scripts/measure-render-performance.mjs capture stability-after
node scripts/measure-render-performance.mjs soak stability-before stability-after --cycles=200
```

### 時間・障害を加速した単体テスト

- 接続開始・認証待ちが停止し、closeイベントも発生しない場合の復帰。
- heartbeat応答なし、送信例外、transport error、認証拒否、古いソケットのイベント。
- offline/onlineを500回反復。接続中のheartbeatタイマーは1個、破棄後は0個。ライフサイクルイベント購読の解除も確認。
- 正常なheartbeat応答を7日分（20,160回）仮想時計で実行。ソケットは1個のまま、タイマー数も一定。
- 可視状態の購読100件を500回登録・解除し、毎回すべての対象が解放されることを確認。
- 保存を失敗させながら2,000件の診断ログを追加し、保持は500件、予約タイマーは最大1個。保存が復旧した後の書き込みと、再失敗時の消去も検証。

`npm run check`、全363テスト（36ファイル）、`npm run build`が成功。

## 範囲と限界

ブラウザ側は部品の反復マウント試験、WebSocket側はモックと仮想時計による試験である。実サーバーに接続した7日間の連続稼働、OSスリープ復帰、サーバー再起動を含む長時間E2Eは実施していない。今回の結果は復帰ロジックと監視リソースの増加防止を裏付けるが、実環境での長期安定性の保証ではない。
