# 長時間運用向けの待機処理改善（2026-09-16）

作業ブランチ: `codex/long-running-performance`。
既存の設定画面改善などの未コミット変更を保持した状態から作業した。
今回の比較基準は HEAD ではなく、その既存変更を含めて性能改善直前に作成したビルド。

## 今回の実装

- 診断の定期計測を App から DiagnosticsColumn に移し、計測による状態更新を診断ペイン内に限定。
- IntersectionObserver で診断ペインの可視性を判定。画面外や非表示では2秒周期の計測を停止し、再表示時に更新。
- 診断とお気に入りのタイマーは、タブ非表示中に停止。表示復帰時は一度更新し、その完了後に次のタイマーを設定。
- お気に入りには元から非表示中の取得防止、取得日時による再取得抑制、同時取得防止がある。今回はその保護を維持し、呼び出し元の不要なタイマー発火も抑制した。
- 非同期処理の完了後に次回を予約するため、遅い取得処理に更新が重ならない。解除後や非表示中に処理が完了してもタイマーを復活させない。

投稿一覧の仮想化とチャンネルキャッシュの件数制限は今回の対象外。

## 計測方法

`e2e/idle-performance.spec.ts` で実際のビルド済み拡張機能を Chromium に読み込む。
ローカルのテスト用 API、診断・お気に入りの2ペイン、1600×900の画面を使用。
変更前後を順番に実行し、各状態を実時間30秒ずつ計測する。

1. 表示中
2. タブ非表示相当
3. 診断ペイン非表示
4. 再表示後

タブ非表示は拡張機能の実行環境で `document.hidden` と `visibilityState` を模擬し、イベントを通知する。
診断ペインの非表示は実際のDOMの表示を切り替え、実際の IntersectionObserver で検出する。
これはOSのスリープ・復帰やブラウザーのタブ破棄を再現する試験ではない。

- 診断計測回数: 診断処理が利用する `document.getElementsByTagName("*")` の呼び出しを計数。
- 処理時間: CDP `TaskDuration` の差分。ページ全体と計測自体の処理を含み、診断処理単体のCPU時間ではない。
- メモリ: 各区間の前後でGCを実行した後の JavaScript ヒープ量を取得。
- DOMノード数とイベントリスナー数も区間前後で比較。

短時間・小規模・各1回の比較なので、CPU時間の削減率や一日中運用した際の安定性を一般化しない。
お気に入りの投稿データがない計測用画面なので、お気に入りの通信量の削減率もこの計測からは判断しない。

## 実測結果

| 状態（各30秒） | 診断計測回数 前→後 | TaskDuration 前→後 | GC後ヒープ増分 前→後 |
| --- | ---: | ---: | ---: |
| 表示中 | 15 → 15 | 58.0 → 37.8 ms | 245.1 → 136.9 KiB |
| タブ非表示相当 | 15 → 0 | 43.2 → 11.0 ms | 20.2 → 0.8 KiB |
| 診断ペイン非表示 | 15 → 0 | 35.4 → 6.9 ms | 11.1 → 6.7 KiB |
| 再表示後 | 15 → 15 | 72.2 → 61.3 ms | 73.6 → 63.2 KiB |

全区間で、DOMノード数・イベントリスナー数の増分は変更前後とも0。API回数は前後とも順に0・1・0・8で、今回の計測では通信削減はない。
ヒープ増分は短時間の初期化・内部キャッシュなどの影響を含むため、リーク量とは解釈しない。
詳細値と比較ビルドのSHA-256: [計測JSON](idle-performance-2026-09-16.json)。

## 再現

PowerShellで `npm run build` を実行した後:

```powershell
$env:DECK_PERF_PHASE_MS = '30000'
npx playwright test e2e/idle-performance.spec.ts --workers=1
```

比較用ビルドは `DECK_PERF_EXTENSION` に指定し、変更前の非表示時計測を許容する場合は `DECK_PERF_BASELINE=1` を設定する。
`DECK_PERF_REPORT` を指定するとJSONをそのパスにも保存する。通常はPlaywrightのテスト出力に添付される。

## 長時間に関する検証範囲

単体テストでは仮想時計を8時間進め、非表示中に処理やタイマーが増えないことを確認する。
また、200回の開始・非表示・復帰・解除を繰り返し、タイマーと登録イベントが残らないことを検証する。
実時間8時間の耐久試験、実サーバーの大量投稿、WebSocket切断・復帰、OSスリープは今回未検証。
