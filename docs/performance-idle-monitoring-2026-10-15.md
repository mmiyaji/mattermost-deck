# 待機処理の性能改善と変更前後の比較（2026-10-15）

今回の改善では、投稿更新に伴うページ全体のダイアログ検索を約67%削減し、非表示中の定期検索を停止できた。CPU処理時間・メモリ使用量・通信量の改善は、今回の計測からは確認できていない。

今回の比較は、性能改善直前の `fd8fecc` と改善後の `ec2c96f`。変更前には以前の待機処理改善とウィンドウ幅調整の修正が既に含まれている。最初の公開版と現在の版を同じ条件で測定した結果ではない。

## これまでの動作から何が変わったか

| 対象 | 改善前の動作 | 現在の動作 | 実施時期 |
| --- | --- | --- | --- |
| 診断の定期計測 | 非表示中や診断ペインが画面外でも2秒周期で計測 | 非表示中・画面外では停止し、再表示時に更新 | 以前の改善（9月16日） |
| 診断結果の更新 | アプリ全体で診断状態を管理 | 診断ペイン内で状態を管理し、更新の影響を限定 | 以前の改善 |
| お気に入りの定期処理 | 非表示中の取得は防いでいたが、タイマー自体は動作 | 非表示中はタイマーも停止。重複取得防止とキャッシュは維持 | 以前の改善 |
| APIヘルス確認 | 非表示中も定期タイマーが動作 | 非表示中は停止。表示復帰時に確認処理を実行し、必要に応じてAPIを取得。非同期処理の重複も防止 | 今回 |
| 画面遷移の補助監視 | 非表示中も5秒ごとに状態を確認 | 非表示中は停止し、表示復帰時にすぐ状態を確認 | 今回 |
| ダイアログ監視 | 投稿行のクラス・スタイル・子要素の変更でもページ全体を検索 | ダイアログ候補・その親要素・追加された要素に関係する変更だけを処理 | 今回 |
| 多数の要素追加時の処理 | 今回の変更前には候補追跡処理なし | 重複チェックに親要素の走査を使い、テキストだけの要素では子要素の検索を省略 | 今回 |
| 認証状態の定期確認 | セッション失効を検知するため継続 | 継続 | 維持 |

## 今回の実測比較

250件の投稿を模した行を使い、10秒間に4回、行の置き換え・クラス・スタイル・テキストの更新を行った。同じ条件で変更前後をそれぞれ3回測定した。

| 指標 | 変更前 | 変更後 | 確認できた変化 |
| --- | ---: | ---: | --- |
| 表示中のページ全体のダイアログ検索（10秒×3回） | 6・6・6回 | 2・2・2回 | 各回で4回減少、約67%削減 |
| 非表示相当のページ全体検索（95秒） | 19回 | 0回 | 非表示中の定期検索を停止 |
| 投稿更新時の部分検索（10秒×3回） | 0・0・0回 | 0・0・0回 | 今回のテキスト中心の行では追加検索なし |
| ページ全体の処理時間の中央値（10秒区間） | 31.864 ms | 32.688 ms | 改善は確認できず |
| ページ全体の処理時間の範囲 | 28.578～32.787 ms | 27.403～36.181 ms | 前後の測定範囲が重なる |
| 非表示中のAPIヘルス確認の通信 | 0回 | 0回 | 通信削減は確認できず |
| 非表示中の認証確認の通信 | 2回 | 2回 | 必要な認証確認は維持 |

変更後も表示中は5秒周期の補助監視が残るため、10秒あたり2回のページ全体検索が発生する。通常の投稿更新を契機とする追加検索を削減した。

APIヘルス確認は、変更前でも最初の90秒周期の実行時点で「アプリの準備完了後、90秒以上更新がない」という条件を満たさず、通信が発生しなかった。この測定でAPI通信が減ったとは言えない。非表示中のタイマー停止と復帰の動作は単体テストでも確認している。

メモリ増分はサンプルごとにばらつきがあり、リーク量とは解釈しない。最初の区間では両版ともテスト用の行の追加によりDOMノードが500増加し、その後の区間ではノード数の増分は0だった。

## 以前の改善で確認できた変化

9月16日の計測では、診断の不要な計測を止める効果を確認している。今回とは対象・測定時間・比較ビルドが異なるため、削減率や処理時間を足して「最初からの総改善率」とすることはできない。

| 状態（各30秒、各1回） | 診断計測回数：改善前→後 | ページ全体の処理時間：改善前→後 |
| --- | ---: | ---: |
| 表示中 | 15→15回 | 58.0→37.8 ms |
| タブ非表示相当 | 15→0回 | 43.2→11.0 ms |
| 診断ペイン非表示 | 15→0回 | 35.4→6.9 ms |
| 再表示後 | 15→15回 | 72.2→61.3 ms |

これまでの改善を通じて、診断・お気に入り・APIヘルス確認・画面遷移の補助監視を、表示状態に応じて休止するようになった。以前の計測条件と限界は[9月16日のレポート](idle-performance-2026-09-16.md)を参照。

## 操作への影響と確認結果

- 単体テスト421件、型チェック、ビルドが成功。
- 画面・チャンネル切り替えのブラウザテスト3件が成功。ページの再読み込みや不要な再取得が起きないことを確認。
- 表示復帰後750 ms以内に、補助監視によるページ全体検索が1回発生することを確認。
- ダイアログ表示時はDeckが背面に回り、非表示・削除すると通常の重なり順に戻ることを確認。Deckのルート要素は維持される。

ダイアログの操作確認は、投稿更新3秒・非表示相当1秒の短い別試験で実施した。95秒の性能測定では、測定後のダイアログ確認がテスト用要素の寸法不足で失敗した。テスト用ダイアログに表示領域を与えて操作確認を再実行し、成功した。失敗した試験のダイアログ状態は結果から除外している。

## 計測方法と限界

一時的なプロファイルでChromiumにビルド済み拡張機能を読み込み、ローカルのMattermost相当APIとテスト用DOMで比較した。実際のMattermost投稿一覧の描画性能や、投稿一覧の仮想化は測定していない。

検索回数は、拡張機能の実行環境でダイアログ判定用の `querySelectorAll` を数え、ページ全体の検索と要素内の部分検索を区別した。処理時間はCDPの `TaskDuration` 差分で、テスト画面・拡張機能・計測処理を含むページ全体の値。CPU使用率そのものではない。

非表示状態は、拡張機能の実行環境で `document.hidden` と `visibilityState` を変更し、`visibilitychange` を通知して模擬した。OSでのウィンドウ最小化・スリープ・復帰や実時間8時間の耐久試験ではない。詳細な測定値は[結果JSON](performance-idle-monitoring-2026-10-15.json)を参照。

## 再実行方法

変更前後の拡張機能ビルドを別のディレクトリに保存し、PowerShellで同じ試験をそれぞれ実行する。

```powershell
$env:DECK_PERF_EXTENSION = (Resolve-Path '.tmp-review/perf-idle-monitoring/baseline').Path
$env:DECK_PERF_BASELINE = '1'
$env:DECK_IDLE_REPEATS = '3'
$env:DECK_IDLE_PHASE_MS = '10000'
$env:DECK_IDLE_HIDDEN_MS = '95000'
npx playwright test e2e/idle-monitoring-performance.spec.ts --workers=1
```

変更後は `DECK_PERF_EXTENSION` を `.tmp-review/perf-idle-monitoring/after` に変更し、`DECK_PERF_BASELINE` を削除する。`DECK_PERF_REPORT` でJSONの保存先を指定できる。短い操作確認は `DECK_IDLE_REPEATS=1`、`DECK_IDLE_PHASE_MS=3000`、`DECK_IDLE_HIDDEN_MS=1000` で実行する。
