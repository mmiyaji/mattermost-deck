# 追加レビューへの対応

| 指摘 | 対応 |
| --- | --- |
| 1・4 移行前の全件読み込み／未移行データの削除 | 永続的な移行済み判定を先に実施。実際に取り込んだキーとSHA-256だけを移行トランザクション内に記録し、旧領域の清掃はコミット後に行う。再試行は対象キーだけを取得し、書き換えられた旧レコードを残す。完了済みの移行は旧領域を再走査しない |
| 2・7 初期の空白行／画面外の要約 | 最初の表示範囲だけ詳細を描画する。通常は最大24行、コンパクトは最大80行。表示領域の高さと上下方向から範囲を決め、画面外は固定高さと軽量な1行要約にする。500行すべての詳細は描画しない |
| 5 圧縮・清掃失敗で確認操作まで失敗 | 圧縮と確認前後の清掃は再試行可能な付随処理にする。確認・未確認への変更そのものの保存失敗は通知し、未確認投稿と判断を保持する |
| 6 Worker不達時の復旧 | 初回読み込み失敗は空の正常状態として扱わず、確認操作と取り込みを止める。確認済みデータを再取得する再試行を追加。拡張コンテキスト失効時はページ再読み込みを案内し、移行後に空になった旧領域へフォールバックしない |
| 8 全アカウント共通キュー | 操作をサーバー・アカウントのprefixごとに直列化。通知もprefix別に順序を保ちながら、コミット済みの保存や読み込みを待たせない |

読み込み失敗中は「未確認なし」や件数0を表示せず、件数を未確定として扱う。再試行では最後の正常な値を保持し、読み込み途中の変更通知を重ね合わせる。

清掃のキー照合と削除は `chrome.storage.local` とIndexedDBをまたぐため、単一トランザクションにはできない。削除直前の指紋照合で確認できた旧レコードだけを対象にする。確認後と削除の間に旧バージョンが同じキーを書き換える競合までは、Chrome Storage APIの制約上完全には排除できない。

表示範囲の初期描画は空白の軽減を目的とし、画像読み込み・折返し・ウィンドウ幅変更などによる高さ変化をゼロにする保証ではない。既に測定した行の高さとブラウザーのスクロールアンカーを引き続き利用する。

指摘3のスケジューラ全件走査は、大規模キューでの改善候補として残す。現行負荷で主要因と確認できていないため変更しない。改善時は優先度に加えてGET／POSTの実行可否を維持する。指摘9の32要素ソート、10の設定変更時クールダウン、12の旧形式単一スコープは現行仕様を維持する。11の待機タイムアウトは独立したリクエストごとのタイマーが既に存在するため変更しない。
